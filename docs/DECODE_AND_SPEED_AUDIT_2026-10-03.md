# 解码漏检与速度审计（2026-10-03）

本次按 `BENCHMARK_AND_COMPARISON_GUIDE.md` 运行 22 组 WAV，并在同一台 Intel i5-8265U（4 核 8 线程）上对照当前 Rust 代码与仓库内的 Fortran 参考源码。对照对象是 `tests/wav/*.txt`，这些文本按交接手册说明由 `wsjtx-lib` **或** `ft8_lib` 生成，不能把每条差异直接解释为 Rust 相对同一版本 WSJT-X 的回归。下述“匹配”“漏检”“额外”均指与文本夹具的一致性；额外结果的真实性未逐条核实。

**本页第 1–4 节记录修复前的诊断基线与消融过程；当前代码的复测结果见第 6 节。**

## 1. 当前基线与计数问题

使用 `cargo test --release --test full_diag_report -- --nocapture`，配置为 3 Pass、`sync_min=1.4`、`deep_search=true`、频漂开启：

| --- | ---: | ---: |
| 参考文本 | 362 | 362 |
| Rust 输出 | 341 | 341 |
| 匹配 | 315 | 319 |
| 报告漏检 | 47 | 43 |
| 基准外输出 | 26 | 22 |
| 参考召回率 | 87.02% | 88.12% |

交接手册写的“36 条漏解”已不是当前代码的结果。原 `normalize_msg` 只识别以 `>` 结尾的 `<...>`，没有识别当前解包器产生的 `<HASH>[HINT]`。四条实际上已译出的消息因此被误列为漏检：`websdr_test7` 的 457 Hz 两条、`191111_110645` 的 1114 Hz、`191111_110700` 的 2111 Hz。测试现已修正此格式，并移除了按 SNR 猜测漏检原因、把全部基准外输出称为“真实信号”的描述。

现有匹配仍只比较归一化后的前三个词与 ±15 Hz 频差，不校验 DT，且允许文本包含关系；本报告的计数遵循这一既有定义，不把它当作独立的射频真值鉴定。

## 3. 消融的整体代价

这些实验用临时环境开关改动相应常量后执行同一个 `full_diag_report`；诊断开关已从生产代码移除。数字仍采用原测试匹配逻辑，以便与 315 基线直接相减。

| 配置变化 | 匹配 / 362 | 基准外输出 | 结论 |
| --- | ---: | ---: | --- |
| 原配置 | 315 | 26 | 基线 |
| 每轮最多 600 候选 | 321 | 41 | 挽回 6 条，也多出 15 条基准外结果 |
| 四路都尝试 OSD | 321 | 36 | 挽回另 6 条，增加计算与基准外结果 |
| 两者组合 | 329 | 55 | 挽回 14 条；基准外结果大幅增加，真实性待核验 |
| 600 候选且 `sync_min` 从 1.4 降到 1.1 | 321 | 42 | 对比单纯 600 候选未增加匹配 |
| 仅把 OSD 硬错误上限 30 改为 36 | 313 | 51 | 859 Hz 恢复 1 条，但 `websdr_test8` 损失 3 条原本匹配；不能直接全局放宽 |
| 取消“第二轮仅新增 1 条就停止” | 315 | 26 | 本批样本没有召回增益 |

参考实现源码中 `MAXCAND=600`、四路常规软信息都可运行混合 BP/OSD、最终硬错误上限 36。Rust 的更强剪枝确实节省时间，但直接改回参考值会改变假解码和消减反馈，不能按单一召回指标决定默认值。

复核消融时，每项均从干净源码单独修改后运行同一命令：候选实验把 `pipeline.rs` 的 `max_cands` 三轮都设为 600；OSD 实验把 `extract.rs` 的 `osd_passes` 设为 `&[&llra, &llrb, &llrc, &llrd]`；硬错误实验把深搜 `max_err` 设为 36；提前停止实验去掉 `ipass >= 2 && pass_new_decodes <= 1` 子句。组合实验同时应用前两处。降门限实验在 600 候选基础上把测试配置的 `sync_min` 设为 1.1。每次运行 `cargo test --release --test full_diag_report -- --nocapture`，然后恢复改动；本次提交保留默认译码参数。

## 4. 速度热点与可行改进

在本机原配置 22 组 WAV 的逐 Pass 计时合计约 **10.28 s**：候选搜索 1.56 s、全长 FFT 0.40 s、并行提取/译码 5.60 s、相干消减 2.79 s。计时打印保留两位小数，因此分项和有舍入误差。`profile_bench` 的单次 OSD Order2 约 **3.461 ms**，BP 约 **0.110 ms**；`websdr_test5` 标准 2 Pass 为 0.15 s，深度 3 Pass 为 0.38 s。优先优化译码与消减，单独压缩 192k FFT 收益有限。

1. **消除重复 BP。** `extract.rs` 先对四路各调用一次 BP；失败后又通过 `decode174_91` 对 `llra`、`llrb` 重跑 BP 才进入 OSD。让首次 BP 失败返回保存的后验 LLR，直接送 OSD，可在不改变判决公式的前提下省掉每个失败候选 1–2 次 BP。以相同输入比较逐候选译码结果与端到端耗时。
2. **按需生成软信息。** 当前在尝试 `llra` 之前已经计算全部 1/2/3 符号度量；`nsym=3` 需枚举 512 种组合。先计算 `llra/llrd`，仅在前一路未成功时计算 `llrb/llrc`，可减少强信号候选的无效工作。需验证 22 组消息集合完全不变。
3. **OSD 在 CRC 前仅恢复信息位。** `osd.rs::check_candidate` 对每个约 4 千个测试向量都先还原 174 位原顺序码字，随后只用前 91 位查 CRC。预计算 MRB 到原信息位的映射，并用打包位异或生成前 91 位；CRC 通过后才还原完整 174 位并算软距离。现有性能文档所称“CRC 前不恢复完整码字”与实际代码不符；此项应单独基准并核对每个候选的最小软距离结果。
4. **预计算 Costas 7 音调背景和。** `sync.rs` 在频点 × 时延 × 21 个同步符号内反复对 7 个音调求和。把每帧每频点的 7 音调能量和预计算一次，可减少内层重复访存与相加；保持候选排序、门限及召回不变后再比较搜索耗时。
5. **消减波形的相位更新与缓存。** `subtract.rs` 对 151,680 个采样逐点调用 `rem_euclid`，且每条已译出信号做一对 180k 复数 FFT。由于常规 100–3500 Hz 的相位步进为正且小于一圈，可用有界条件减法代替通用取模；重构 `Vec` 与线程缓存也可跨轮复用。先比较残差 RMS、后续 Pass 的候选与消息，再测速度。分块 FFT/overlap-save 属较大改动，需实测才可判断收益。

选择召回/速度折中时，优先做**按需扩展候选和 OSD**：先跑当前快速集合，仅对同步质量较高、尚未覆盖的频时区域扩展搜索。放宽候选或错误数会反馈到消减波形，必须同时记录匹配、基准外文本、耗时与具体被替换的消息。当前 `sync_pow_init < 1.0` 比较的是未归一化的功率量，实测目标候选通常为 `10^9` 以上，不能把这条判断当作已验证的有效噪声剪枝。

## 5. 后续验证重点

- 对七条“入选但未译出”的候选保存每路 LLR、BP 校验子轨迹、OSD 最优距离与对应文本，先检查 `websdr_test1` 598 Hz 和 `websdr_test7` 2324 Hz。本文只把它们定位到处理段，未把邻频干扰、相位漂移等猜测当作最终物理成因。
- 若产品需要保留同文不同频的多路发送，应把文本去重与时频冲突分开：相同文本在相同频时才合并，不同文本的近邻信号须有独立波形证据。原版 Fortran 也有全局文本去重，因此需先确定产品语义和夹具来源。
- 更新交接手册中的旧计数，以及 `profile_bench` 的项目清单：当前测试只测 OSD、BP 和整段标准/深搜，并没有手册所写的 CRC 与单条消减微基准。

## 6. 本轮修复与优化后的复测

已修复 `pipeline.rs` 中不同报文的时频近邻互斥。原规则仅凭频差 <8 Hz、时间差 <0.20 s 覆盖或丢弃已经通过 LDPC 与 CRC 的另一条报文。本轮仍按完整文本全局去重，与仓库内 Fortran 的行为保持一致；不同文本不再互斥。`websdr_test9` 的 `CQ PY1SX GG87`、`191111_110615` 与 `110645` 的 `G1XJM HA7JIV JN97` 因此恢复。新增 WAV 回归测试覆盖其中两组相邻不同报文。

译码路径复用四路首次 BP 失败时保存的后验 LLR，进入 OSD 时不再对前两路重复运行 BP。OSD 每个候选先仅按预计算映射取出 91 个信息位做 CRC；CRC 通过后才恢复完整 174 位码字并计算软距离。前后完整诊断输出的匹配、未匹配和额外消息集合保持一致。

| 指标（22 WAV，3 Pass 深搜） | 修复前 | 修复并优化后 |
| --- | ---: | ---: |
| 参考文本 | 362 | 362 |
| Rust 输出 | 341 | 345 |
| 匹配 | 319 | 322 |
| 未匹配 | 43 | 40 |
| 基准外输出 | 22 | 23 |
| 参考召回率 | 88.12% | 88.95% |
| 夹具匹配精确率 | 93.55% | 93.33% |

`profile_bench` 的 OSD Order2 单次耗时从修复前约 3.461 ms 降至约 2.966 ms，约快 14%；BP 算子本身未修改。一次完整诊断测试从 8.78 s 到 8.66 s，差异接近运行波动，**不能据此宣称整套流水线有稳定的加速比例**。本轮性能收益明确体现在 OSD 微基准和避免重复 BP 的代码路径上；建议在固定 CPU 频率和线程数后多次运行，才评价端到端收益。

剩余 40 条未匹配中，原先的 10 条同文不同频记录仍受全局文本去重影响；这是当前参考实现也采用的语义。扩大候选池、后两路 OSD、放宽硬错误数等消融结论仍有效，但它们的组合结果需要在修复后的代码上重测，不能把第 3 节数字直接相加预测新召回率。
